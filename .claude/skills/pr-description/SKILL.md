# Описание pull request

Описание PR пишется для ревьюера, которому нужно решить, безопасно ли это мерджить, и для
человека через год, который придёт сюда из `git blame`. Поэтому важнее всего не перечень
файлов — его видно в диффе, — а **почему** сделано именно так и **что проверено**.

## Собрать материал

```bash
git log --oneline main..HEAD
git diff --stat main..HEAD
```

Прогони тесты и запиши реальный результат — в описание идут те цифры, которые ты видел, а не
те, которые ожидаешь:

```bash
export JAVA_HOME="/c/Program Files/Java/jdk-24"
./mvnw test
```

## Заголовок

Conventional commits, как и в коммитах, плюс ссылка на раздел спеки:

```
feat(client-service): Client Profile MVP — create, read and lookup (SPEC §5.3)
fix(db): create idempotency_keys, missing since SPEC §4.6
```

GitHub подставляет заголовок из имени ветки (`Feat/client profile mvp`) — его всегда надо
заменить.

## Структура тела

**Одно-два предложения о том, что это.** Без разогрева.

**Таблица эндпоинтов / изменений** с идентификаторами user story или правил из SPEC, если PR
добавляет API.

**«Баги, найденные по дороге» — отдельным разделом.** Если при работе нашлась поломка,
существовавшая до тебя, она заслуживает собственного раздела и собственного коммита: её
ревьюят иначе, чем фичу, и иногда её нужно черри-пикнуть отдельно. Для каждого: что было
сломано, что бы из-за этого произошло, как починено.

**«Решения, о которых стоит знать».** Только то, что ревьюер не выведет из диффа: почему
выбран этот подход, какая альтернатива отвергнута и почему, какое место в коде окажется
единственным, которое придётся менять при развитии. Если правка спеки была частью изменения —
скажи прямо, что и почему поменял.

**«Тесты».** Сколько, против чего, какие идентификаторы SPEC покрыты, и как их прогнать
локально. Не «покрыто тестами», а конкретика.

**«Чего в этом PR нет».** Явный список отложенного. Это не признание в неполноте, а то, что
не даёт ревьюеру искать несуществующее и оставляет след для следующего среза работы.

## Правила

- Пиши, что действительно проверено запуском, и отдельно — что выведено чтением. Никогда не
  утверждай, что тесты проходят, не прогнав их.
- Никакого PII и никаких секретов в примерах: описание PR публично внутри организации.
- Идентификаторы SPEC (`CP-BR-03`, `IL-EC-07`) — это стабильные ссылки, цитируй их.
- Если считаешь, что спека неверна, скажи это в описании, а не правь код под неё молча.
- Не пересказывай дифф файл за файлом. Ревьюер откроет вкладку Files changed сам.

## Хвост

Описание PR заканчивается строками атрибуции:

```
🤖 Generated with [Claude Code](https://claude.com/claude-code)

<ссылка на сессию>
```

## После создания

- CI в репозитории **не настроен**: `.github/workflows` отсутствует, поэтому автоматически не
  запустится ничего и зелёных галочек не будет. Их отсутствие не означает, что всё хорошо —
  скажи в описании, что прогнал локально.
- Пройди по вкладке Files changed сам: ревью собственного диффа на GitHub ловит то, что не
  видно в редакторе.
- При мердже выбирай **Merge commit**, если коммиты разделены осмысленно. Squash склеит фикс
  блокера с фичей в один неразбираемый ком.
