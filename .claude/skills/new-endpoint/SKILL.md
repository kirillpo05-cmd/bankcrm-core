# Новый эндпоинт

Домен регулируемый: аудируемость и контроль доступа здесь функциональные требования. Эндпоинт
не готов, пока каждое реализованное правило не процитировано в имени теста.

## 1. Прочитай контракт, не угадывай его

Открой раздел API для своего модуля: `SPEC.md` §5.3 (clients), §6.3 (interactions), §7.3
(tasks), §8.3 (audit), §9.3 (RBAC). Таблица эндпоинта задаёт **точные** HTTP-коды и значения
`code`. Реализуй их, а не правдоподобную альтернативу.

`404` там, где спека говорит `404`, даже если `403` кажется честнее, — это ER-01, и оно
намеренное: иначе по коду ответа можно перебирать существование записей.

Прочитай также бизнес-правила (§*.4) и краевые случаи (§*.6) — их идентификаторы пойдут в
имена тестов. И `.claude/rules/<service>.md` для сервиса, который трогаешь.

Определи, какой сервис владеет нужными таблицами (`CLAUDE.md` → Architecture). Захотелось
прочитать чужую таблицу — остановись: ответ либо REST-вызов, либо денормализованное поле в
событии.

## 2. Слои

`Controller` → `Service` → `Repository`. Контроллер занимается HTTP: биндинг, валидация,
статусы, заголовки. Решения принимает сервис. Контроллер никогда не ходит в репозиторий
напрямую, и никаких `@PreAuthorize` с ролями.

Готовые образцы в репозитории:

- `api/ClientController.java` — тонкий контроллер, идемпотентность, ETag, Location
- `service/ClientService.java` — правила, транзакции, scope
- `service/ClientAccess.java` — permission + scope → решение о записи
- `service/ClientEvents.java` — события, включая отказ в отдельной транзакции
- `persistence/ClientRepository.java` — `JdbcClient`, шифрование на входе и выходе

## 3. DTO и валидация

Запросы и ответы — `record`, отдельные от доменных типов в обе стороны. Маппинг явный:
рефлективный маппер однажды молча вынесет новое чувствительное поле в ответ.

Bean Validation на краю (`@NotBlank`, `@Email`, `@Past`, `@Size`) **и** `CHECK` в БД.
Валидируй на обоих краях: БД — последняя линия, а не единственная.

Неизвестное поле в теле — это `400`, а не молчаливое игнорирование: `FAIL_ON_UNKNOWN_PROPERTIES`
уже включён в `JsonConfig`.

## 4. Четыре вещи, которые ломаются чаще всего

**Authorization.** Спрашивай `AccessPolicy` про permission + scope, никогда про строку роли.
Несколько ролей объединяют права и берут широчайший scope (RB-BR-03). Отказ, показанный
пользователю как `404`, всё равно обязан породить `PERMISSION_DENIED` в аудите — и записать
его **в отдельной транзакции**, иначе он откатится вместе с отклонённым запросом.

**Outbox.** Каждая мутация пишет строку в `outbox_events` в **той же** транзакции, что и
бизнес-изменение. `KafkaTemplate.send()` из сервисного метода не вызывается никогда —
публикует relay. Чувствительные значения в `changedFields` маскируются там, где событие
конструируется, чтобы plaintext не доехал до брокера (AR-01).

**Идемпотентность и версии.** `POST`-создание требует `Idempotency-Key`; `PATCH`/`DELETE` на
версионируемом агрегате требует `If-Match`, отдаёт `412` при отсутствии заголовка и `409` с
текущим состоянием сервера в `details[0].current` при устаревшей версии. UI строит из этого
payload диф, поэтому поле обязано быть заполнено.

**Коды ошибок.** Стабильный `code` из каталога §4.4 плюс сущностные коды сервиса. Фронтенд
переключается по `code`, а не по `message`, — переименование ломающее. Именованные
ограничения БД маппятся через `ConstraintError.Registry` (`ClientConstraintErrors`).

## 5. Пагинация

Offset — только для ограниченных админских списков. Лента взаимодействий и аудит-лог —
**keyset**. Никогда `OFFSET` по большой таблице.

## 6. Тесты

- Один тест на каждое реализованное правило, названный его идентификатором:
  `void derivesTeamFromOwnersPrimaryTeam_CP_BR_03()`.
- Основной сценарий плюс минимум два краевых случая (`*-EC-*`) из перечисленных для
  эндпоинта.
- Тест авторизации на каждую роль; матричный тест «роль × эндпоинт» должен продолжать
  проходить.
- Интеграционные — на Testcontainers с настоящими PostgreSQL и Kafka. Мок брокера прячет
  ровно те баги порядка и переотправки, ради которых тесты и нужны.
- Отдельно проверь то, что легко сломать незаметно: что в `outbox_events` появилась строка,
  что в её payload стоит `***MASKED***` и **нет** plaintext, что чтение вне scope даёт `404`.

```bash
export JAVA_HOME="/c/Program Files/Java/jdk-24"
./mvnw -pl src/<service> -am test
./mvnw spotless:apply    # форматирует весь реактор — закоммить только свои файлы
```

## Чеклист

- [ ] HTTP-коды и значения `code` совпадают с таблицей эндпоинта в SPEC.
- [ ] `permission + scope` проверяются до бизнес-логики, через `AccessPolicy`, не по роли.
- [ ] Отказ вне scope отдаёт `404` и пишет `PERMISSION_DENIED` в своей транзакции.
- [ ] Мутация пишет outbox-строку в той же транзакции; прямых вызовов Kafka нет.
- [ ] Чувствительные значения в `changedFields` замаскированы.
- [ ] Создание требует `Idempotency-Key`; версионируемая запись требует `If-Match` и отдаёт
      `409` с `details[0].current`.
- [ ] Тела запросов и ответов нигде не логируются, PII нет в сообщениях исключений.
- [ ] Каждое правило процитировано в имени теста; покрыт основной сценарий и два краевых.
- [ ] Всё прогнано, сборка зелёная.
