# PROJECT_IDEA.md — Client360

## 1. Проблема

Менеджер банка тратит 15–20 минут на сбор полной картины по клиенту перед звонком или встречей: история обращений хранится в одной системе, статус продуктов — в другой, личные заметки — в Excel или на бумаге. Из-за этого:
- менеджер задаёт клиенту вопросы, ответы на которые уже есть в системе;
- супервайзер не видит просроченные задачи по клиентам в реальном времени;
- нет единого аудита: кто и когда менял данные клиента.

Целевая метрика: сократить время подготовки к контакту с клиентом с 15–20 минут до 2–3 минут.

## 2. Решение

Пошаговый процесс:
1. Менеджер открывает единую карточку клиента по email/телефону/ID.
2. Карточка показывает: контактные данные, статус KYC, список продуктов, ленту всех взаимодействий (звонки, тикеты, заметки).
3. Менеджер добавляет новое взаимодействие (заметку, тикет, задачу-напоминание).
4. Система логирует каждое изменение в аудит-журнал (кто, когда, что изменил).
5. Супервайзер видит дашборд с просроченными задачами по всем менеджерам своей команды.

Каждый шаг — отдельный модуль:
- Client Profile (карточка клиента)
- Interaction Log (лента взаимодействий)
- Task/Reminder (задачи и напоминания)
- Audit Trail (журнал аудита)
- RBAC (роли и доступ)

## 3. Почему сейчас

- Рост требований к комплаенсу и аудируемости данных в финансовом секторе (GDPR, внутренние банковские регламенты).
- Тренд на консолидацию разрозненных CRM-инструментов в единую "customer 360" карточку.
- Банки инвестируют в модернизацию legacy CRM-систем — тема актуальна для собеседований в финтех/банкинг.

## 4. Целевая аудитория

- **Основная**: менеджеры по работе с клиентами в банке. Задача — быстро находить контекст клиента и фиксировать взаимодействия. Текущий инструментарий: разрозненные системы + Excel.
- **Вторичная**: супервайзеры/тимлиды. Задача — контролировать SLA и просроченные задачи команды.

## 5. Архитектура

Три слоя:

```
[REST API: Spring Boot] → [PostgreSQL: основные данные]
         ↓
[Kafka: события изменений] → [Audit Service: журнал аудита]
```

Стек и обоснование:
- **Java + Spring Boot** — индустриальный стандарт для банковского бэкенда, Spring Security для ролей.
- **PostgreSQL** — ACID-гарантии для финансовых/персональных данных.
- **Kafka** — асинхронная запись аудит-событий без замедления основного API, задел на масштабирование (уведомления, интеграции).
- **Docker + docker-compose** — локальное окружение (API + DB + Kafka) одной командой.

Модули с входами/выходами:
- `client-service`: вход — HTTP-запросы CRUD клиента, выход — JSON-профиль, события в Kafka (`client.updated`).
- `interaction-service`: вход — заметка/тикет, выход — запись в БД, событие `interaction.created`.
- `audit-service`: вход — события из Kafka, выход — неизменяемый лог в таблице `audit_log`.

## 6. Монетизация

Не применимо — внутренний B2B use case (демонстрационный/pet-проект банковского CRM-модуля, не SaaS-продукт).

## 7. Конкуренты

| Конкурент | Что делает | Чего не хватает |
|---|---|---|
| Salesforce Financial Services Cloud | Полноценная CRM с финансовыми модулями | Дорого, избыточно для локальной задачи, сложная кастомизация |
| Microsoft Dynamics 365 | CRM + ERP интеграция | Тяжёлый деплой, vendor lock-in |
| Собственные Excel/легаси-системы банков | Дёшево, привычно | Нет аудита, нет единой карточки клиента, ручной труд |

## 8. План запуска

- **MVP**: Client Profile + Interaction Log (CRUD карточки клиента, добавление заметок/тикетов).
- **v2**: Audit Trail + RBAC (роли manager/supervisor/admin, журнал изменений).
- **v3**: Task/Reminder + дашборд супервайзера с уведомлениями о просрочках.

## 9. Риски

| Риск | Вероятность | Митигация |
|---|---|---|
| Утечка персональных данных клиента | Средняя | Шифрование чувствительных полей (email, телефон) на уровне БД, ролевой доступ |
| Разрастание монолита при добавлении модулей | Средняя | Чёткое разделение на сервисы с самого начала (client/interaction/audit) |
| Несогласованность данных при асинхронной записи аудита | Низкая | Kafka с at-least-once delivery + идемпотентные обработчики |
